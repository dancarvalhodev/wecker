# PHP Modernization Report — `www/bootstrap/Main.php`

> Generated by the `modernize-php` skill. Target PHP version: **8.5**.
> Audience note: explanations assume a junior developer, so each item says *what* to change, *how*, and *why it matters*.

## Summary

`Main.php` is the app's startup orchestrator: its constructor loads `.env`, builds the DI container, creates the Slim app, and registers middleware + routes. The file is already in decent shape — `final class`, typed properties, typed method signatures, and no SQL/security concerns. So this is a **low-effort** polish pass, not a rewrite. The most worthwhile change is replacing the positional boolean arguments to `addErrorMiddleware()` (currently documented with inline `// comments`) with **named arguments**, which makes those flags self-explaining. Beyond that: add `declare(strict_types=1)` for parity with the project's entrypoints, and optionally compute the base path once instead of calling `dirname(__DIR__)` six times.

## Recommendations

### 1. Use named arguments for the `addErrorMiddleware()` flags

**Where:** `Main.php:90–94` (`registerMiddlewares()`)

**What it looks like now**
```php
$errorMiddleware = $this->app->addErrorMiddleware(
    !Application::isProduction(), // displayErrorDetails
    true, // logErrors
    true  // logErrorDetails
);
```

**Suggested change**
```php
$errorMiddleware = $this->app->addErrorMiddleware(
    displayErrorDetails: !Application::isProduction(),
    logErrors: true,
    logErrorDetails: true,
);
```

**Why change it**
When you call a function with a row of bare `true`/`false` values, the reader has no idea what each one *means* without opening the function's definition — which is exactly why someone added the `// displayErrorDetails` comments here. Those comments are a workaround, and comments can drift out of sync with the code (e.g. if two arguments are swapped, the comment still says the old thing but the behaviour is now wrong, and nothing catches it).

**Named arguments** let you label each value at the call site using the *real* parameter name (`displayErrorDetails:`). The label is checked by PHP against the function signature — if you misspell it or the parameter is renamed, you get an error instead of silent breakage. The code becomes self-documenting, so the trailing comments can be deleted.

Gotcha: the name must match the parameter name in the callee exactly. Slim's `ErrorMiddlewareAwareTrait::addErrorMiddleware()` declares them as `$displayErrorDetails`, `$logErrors`, `$logErrorDetails`, so the names above are correct — but if you ever bump Slim to a version that renames a parameter, the named call would need updating too. That's a fair trade for the added clarity and safety.

**Since:** PHP 8.0. **Risk of changing:** none — behaviour-preserving (same values in the same order).

### 2. Add `declare(strict_types=1)` at the top of the file

**Where:** `Main.php:1` (top of file, before `namespace`)

**What it looks like now**
```php
<?php

namespace App\Bootstrap;
```

**Suggested change**
```php
<?php

declare(strict_types=1);

namespace App\Bootstrap;
```

**Why change it**
By default PHP runs in "coercive" typing mode: if a function is typed to take an `int` but you pass the string `"5"`, PHP quietly converts it. That silent conversion hides bugs — e.g. passing `"0"` (a truthy-looking string that becomes `0`) where you meant a real value. `declare(strict_types=1)` switches the *current file* into strict mode, so a type mismatch throws a `TypeError` immediately instead of guessing. You catch the bug at the boundary rather than three layers deeper where the wrong value finally blows up.

`Main.php` itself has few external inputs, so the practical bug-catching payoff here is small — the real reason to add it is **consistency**. Your project's rules note that `declare(strict_types=1)` already appears in entrypoints and routes but isn't applied uniformly across `src/`. A bootstrap file is exactly the kind of "front door" file where matching the entrypoint convention makes sense. The directive is per-file (it only affects calls made *from* this file), so adding it here is safe and self-contained.

**Since:** any modern PHP. **Risk of changing:** behaviour-preserving in practice for this file (no loose type coercions happen here); if a hidden coercion did exist, strict mode would surface it as an error — which is the point.

### 3. Compute the base path once into a `readonly` property

**Where:** `Main.php:48, 62, 63, 66, 67, 68, 85` — every `dirname(__DIR__)` call

**What it looks like now**
```php
Dotenv::createImmutable(dirname(__DIR__))->safeLoad();
// ...
$builder->enableCompilation(dirname(__DIR__) . '/storage/cache');
$builder->writeProxiesToFile(true, dirname(__DIR__) . '/storage/cache');
$builder->addDefinitions(dirname(__DIR__) . '/config/database.php');
$builder->addDefinitions(dirname(__DIR__) . '/config/twig.php');
$builder->addDefinitions(dirname(__DIR__) . '/config/handler.php');
// ...
(require dirname(__DIR__) . '/routes/web.php')($this->app);
```

**Suggested change**
```php
final class Main
{
    private Container $container;
    private App $app;
    private readonly string $basePath;

    public function __construct()
    {
        $this->basePath = dirname(__DIR__);
        $this->loadConfigs();
        // ...
    }

    private function loadConfigs(): void
    {
        Dotenv::createImmutable($this->basePath)->safeLoad();
    }

    private function buildContainer(): void
    {
        // ...
        $builder->enableCompilation($this->basePath . '/storage/cache');
        $builder->writeProxiesToFile(true, $this->basePath . '/storage/cache');

        foreach (['database', 'twig', 'handler'] as $config) {
            $builder->addDefinitions($this->basePath . "/config/{$config}.php");
        }
        // ...
    }
}
```

**Why change it**
`dirname(__DIR__)` (the directory one level above `www/bootstrap/`, i.e. `www/`) is recomputed seven times. It always returns the same value, so this is repeated work and, more importantly, repeated *text* — if the file ever moves and the path logic needs to change, you have seven spots to keep in sync, and it's easy to miss one. Naming it once (`$this->basePath`) gives the value a meaning and a single source of truth.

`readonly` (PHP 8.1) is the right modifier here: the base path is set exactly once in the constructor and must never change afterwards. Marking the property `readonly` means the *language* enforces that — any accidental later reassignment is a fatal error, not a subtle bug. This documents intent ("this is fixed after construction") and protects it at the same time. Note you can't make it a class `const`, because `dirname(__DIR__)` is a runtime function call, not a constant expression — a constructor-assigned `readonly` property is the correct tool.

The `foreach` over the three config names is an optional bonus in the same spirit: it removes three near-identical lines. Keep it only if you find it clearer; the three explicit `addDefinitions()` calls are perfectly fine too.

**Since:** `readonly` — PHP 8.1. **Risk of changing:** behaviour-preserving — same paths produced, just computed once.

## Not changed on purpose

- **The redundant PHPDoc blocks** (`/** @var App $app */` over an already-typed property; `@return void` / `@throws Exception` on typed methods). Normally these doc-only annotations would be candidates for removal since the native types already say the same thing. But your project's `code-style.md` explicitly states this verbose docblock style is intentional and consistent across the codebase — so this file *matches* the convention and shouldn't be "fixed" in isolation. Left as-is deliberately.
- **No pipe operator `|>`, `match`, enums, `array_first/last`, or `clone with`.** These are real 8.5/modern features, but nothing in this file fits them: there's no data-transformation chain to pipe, no value-mapping to `match`, no fixed value set to turn into an enum, and no array/collection work. Recommending them here would be forcing a feature where it doesn't belong.
- **`new ContainerBuilder()` then several setter calls.** This is the builder's documented API; there's no cleaner modern idiom for it.
